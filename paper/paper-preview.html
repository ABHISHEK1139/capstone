Abstract

Frequent-itemset mining and association-rule mining are standard tools for market-basket analysis, recommendation, and categorical pattern discovery, yet current scikit-learn offers no native estimator for them: the feature request (issue #32712) was closed as “not planned” on scope grounds, with maintainers directing the work to a separate, scikit-learn-compatible library. The closest existing library, mlxtend, provides the mining functions but not an estimator API, and it provides no Eclat. We present skarm, a Python library that packages three classic miners — Apriori, FP-Growth, and Eclat — behind a single scikit-learn-style estimator with deterministic rule ordering, explicit candidate-count telemetry, and a bounded-generation mode that reports truncation instead of silently returning partial results. The evaluation protocol compares all three engines plus an mlxtend baseline at matched support thresholds on 25 datasets, with a 30-trial statistical protocol on an 8-dataset subset and exact itemset-agreement checks on every cell. Across 25 datasets (1,650 trial records on one Windows PC), all 157 compared engine pairs agree exactly on frequent itemsets (Δsupp=0.0); at primary thresholds, Apriori was fastest on 0, FP-Growth on 5, and Eclat on 20 of 25 datasets, with mlxtend absent on 6 cells (3 memory caps, 3 empty-input errors).

Keywords: Association-Rule Mining, Frequent-Itemset Mining, Apriori, FP-Growth, Eclat, scikit-learn Compatibility, Auditable Pruning Governor, Reproducibility.

1. Introduction

Problem and Motivation

Frequent-itemset mining (FIM) and association-rule mining (ARM) discover directional implications X ⇒ Y (X ∩ Y = ∅) satisfying support (σ) and confidence (γ) thresholds over an item universe I in a database D of N transactions [1, 2, 4]. While algorithmically mature, integrating these methods into modern Python workflows exposes operational challenges across practitioner roles:

  1. Data Scientists and ML Engineers struggle with fragmented APIs across packages. Existing tools rely on standalone functions over dense DataFrames, lacking compatibility with scikit-learn's standardized fit, transform, and Pipeline abstractions.
  2. Data Engineers and Production Systems face combinatorial candidate explosion (2^|I| - 1). In dense regimes, existing exact miners either exceed memory limits or run unbounded, lacking candidate governors and degradation contracts.
  3. Model Auditors and Compliance Researchers encounter undocumented execution differences, non-standard metric definitions, and opaque edge cases that impede reproducibility, as well as non-deterministic row sorting that corrupts version-controlled tracking.

To serve these distinct user profiles, a modern association-rule mining library must answer three fundamental questions honestly: which patterns were discovered, whether the returned output is mathematically exhaustive or budget-bounded, and what computational cost was incurred across both system resources and algorithmic steps.

The Scikit-Learn Scope Context

In November 2025, a formal community feature request (issue #32712 [7]) proposed a native sklearn.association module exposing an Apriori estimator with fit() and standard rule metrics. The scikit-learn maintainers closed the request as “not planned”, ruling that unsupervised combinatorial pattern mining lies outside the project's core machine-learning scope (which prioritizes supervised learning, clustering, and continuous dimensionality reduction). The maintainers explicitly recommended that association mining is best developed as an external, dedicated, scikit-learn-compatible package (similar to scikit-mine or scikit-learn-contrib). An earlier community discussion (#2662, 2013–2014 [6]) reached the identical conclusion.

Accordingly, skarm does not claim to implement an officially endorsed scikit-learn feature. Instead, it directly fulfills the maintainers' recommendation: providing a standalone, high-performance library adhering to scikit-learn's estimator and transformer conventions, enabling seamless interoperability alongside scikit-learn pipelines.

Three Dimensions of Determinism

A central design objective of skarm is end-to-end determinism as an evaluated engineering and scientific property rather than an unverified assumption. We explicitly formalize three technical tiers of determinism:

  1. Result Determinism: For any transaction multiset D and configuration θ = (σ, γ, M), the frequent itemsets F_σ(D) and rules R_σ,γ(D) are identical regardless of backend mining engine E ∈ Apriori, FP-Growth, Eclat or initial item ordering in D:
    ∀ E_i, E_j:\ F_σ(D | E_i) ≡ F_σ(D | E_j) \ ∧
    max_X ∈ F_σ |supp_E_i(X) - supp_E_j(X)| = 0.0
    This property is empirically certified across all 42 benchmark cells and 157 trial-0 pairwise comparisons (Table 6).
  2. Ordering Determinism: Discovered itemsets and rules are sorted by a strict canonical key to eliminate non-deterministic row shuffling: itemsets by descending support, ascending cardinality, and lexicographical item tokens; rules by descending metric, descending confidence, descending support, and lexicographical antecedent/consequent tokens. This guarantees zero output diff churn across repeated invocations (asserted by test NT-5).
  3. Execution Determinism: When candidate budgets (B_cand) trigger degradation, candidate generation halts via deterministic ordered enumeration, ensuring that bounded executions (F_bounded) recover identical, reproducible pattern subsets within the tested environment across repeated executions.

Research Questions

This investigation evaluates the design, correctness, and empirical scaling of skarm across 25 diverse real-world and synthetic benchmark datasets, structured around five formal research questions:

  • RQ1 (Algorithmic Equivalence): Can three fundamentally distinct mining paradigms (level-wise Apriori, recursive prefix-tree FP-Growth, and vertical tidset Eclat) produce provably identical frequent itemsets and association rules under a unified estimator interface?
  • RQ2 (Comparative Performance and Scaling): How do fit runtime, memory footprint, and transaction throughput scale across varied dataset densities, average transaction lengths, and item catalog sizes?
  • RQ3 (Bounded-Search Safety and Recall): What trade-offs between computational speedup and pattern recall emerge when an auditable resource governor caps combinatorial candidate explosion?
  • RQ4 (Scikit-Learn API and Pipeline Interoperability): Does the estimator satisfy scikit-learn's formal object protocols (cloning, parameter inspection, serialization) and integrate effectively into both final-estimator and intermediate-transformer Pipeline stages?
  • RQ5 (Reproducibility and Observability): Can multi-engine execution telemetry and cross-engine agreement be audited deterministically across independent trial runs?

Capstone Objectives and Contributions

This research represents the KL University Capstone Project framework KLCAP-2026-00340. The core contributions are:

  • Unified Multi-Engine Estimator: We package three classic mining engines (Apriori, FP-Growth, and Eclat) behind a single scikit-learn-compliant AssociationRulesEstimator, ensuring algorithmic comparisons reflect computational mechanics rather than disparate API designs.
  • Auditable Safe-Degradation Governor: We introduce an auditable candidate governor that prevents catastrophic out-of-memory errors by halting search at a user-defined candidate budget, explicitly signaling execution status (EXACT vs. DEGRADED) with machine-readable truncation counts.
  • Engineered O(1) Header-Table Tail Pointers: We augment FP-Tree construction with O(1) direct tail pointers in the frequency header table, eliminating the O(L) linked-list traversal bottleneck on deep clickstream benchmarks (e.g., BMS-POS).
  • Rigorous 25-Dataset Empirical Benchmark: We conduct a comprehensive 1,650-trial empirical evaluation across 25 benchmark datasets spanning 8 application domains, certifying 100% pairwise cross-engine correctness (Δsupp = 0.0) across all 157 evaluated engine pairs.

2. Related work

Classic Mining Paradigms

Frequent itemset mining algorithms generally follow three classic algorithmic paradigms:

  • Horizontal Level-Wise Generation (Apriori) [1]: Generates length-k candidates (C_k) via self-joins of frequent (k-1)-itemsets (L_k-1 ⋈ L_k-1), applies downward-closure anti-monotone pruning (∀ s ⊂ c, s ∈ L_k-1), and scans the entire transaction matrix to compute supports. Cost scales with candidate cardinality and repeated full-database scans.
  • Prefix-Tree Projection (FP-Growth) [2, 3]: Compresses transactions into a compact Frequent Pattern Tree (FP-Tree) in two passes using items sorted by descending frequency (L_1). Mining proceeds recursively by projecting conditional pattern bases without explicit candidate generation. Memory cost is dominated by recursive tree allocations.
  • Vertical Inverted Tidsets (Eclat) [4]: Inverts the transaction matrix into a vertical mapping i T(i), where T(i) is the set of transaction IDs containing item i. Support is computed via set intersection: T(X ∪ Y) = T(X) ∩ T(Y). Equivalence classes partition the depth-first search space. Memory cost scales with tidset length on dense datasets.

Architectural Differentiation of skarm

skarm does not propose a new combinatorial search heuristic. Instead, its research contribution is an architectural, resource-aware framework that: (1) unifies three canonical mining paradigms behind an identical scikit-learn estimator interface, (2) provides an auditable execution contract that guarantees exactness or honestly signals bounded degradation, and (3) delivers granular system and algorithmic telemetry.

3. Methods and System Specification

Formal Problem Formulation

Let I = i_1, i_2, , i_M denote a discrete universe of M unique items. A transaction T ⊂eq I is a non-empty set of distinct items. A transaction database D = (T_1, T_2, , T_N) is an ordered multiset of N transactions. In our formulation, duplicate transaction rows are retained and counted as distinct observations, repeated items within a transaction are idempotently deduplicated (T ≤ftarrow unique(T)), and null or empty transactions are rejected during preprocessing.

Support. For any itemset X ⊂eq I, its absolute transaction support is σ_D(X) = |T ∈ D | X ⊂eq T|, and its relative support is:

supp(X) = σ_D(X)N = |T ∈ D | X ⊂eq T|N
Given a minimum support threshold σ ∈ (0, 1], an itemset X is frequent if supp(X) ≥ σ. The set of all frequent itemsets is defined as:
F_σ = X ⊂eq I | supp(X) ≥ σ

Association Rules. An association rule is an implication of the form X ⇒ Y, where X, Y ⊂ I, X ≠ ∅, Y ≠ ∅, and X ∩ Y = ∅. The itemset X is the antecedent, and Y is the consequent. The rule is valid only if the combined itemset X ∪ Y ∈ F_σ.

Confidence and Numerical Metrics. The confidence of a rule represents its empirical conditional probability:

conf(X ⇒ Y) = supp(X ∪ Y)supp(X)
Given a minimum confidence threshold γ ∈ (0, 1], the set of qualifying association rules is:
R_σ, γ = X ⇒ Y | X ∩ Y = ∅, X ∪ Y ∈ F_σ,
conf(X ⇒ Y) ≥ γ

Formal Execution Contract and Result States

To guarantee honesty under resource constraints, skarm enforces a formal three-state execution contract:

  1. EXACT: The mining engine traversed the complete search space. The returned itemsets F_σ and rules R_σ, γ are provably exhaustive (status_ = "EXACT", is_complete_ = True, is_degraded_ = False).
  2. DEGRADED: The candidate governor interrupted execution because candidate generation, runtime, or memory reached the specified safety cap. The returned itemsets represent a valid, certified subset of true frequent itemsets (F_bounded ⊂ F_exact). Crucially, skarm sets status_ = "DEGRADED", is_degraded_ = True, is_complete_ = False, and records exact candidate counters and degradation reasons in metadata_, ensuring bounded results are never misrepresented as exhaustive.
  3. FAILED: Execution terminated abnormally due to invalid inputs (e.g., non-binary or negative matrices) or configured raise policies (on_candidate_explosion="raise"). In strict accordance with scikit-learn API fail-fast conventions, this state represents an unrecoverable execution outcome signaled via checked exceptions (ValueError, CandidateExplosionError), rather than returning a corrupted fitted estimator instance.

The Tri-Engine Core and O(1) Tail Optimization

Figure 1 details the comparative algorithmic workflows across the three swappable mining engines:

  • Apriori: Implements sparse CSR candidate joins with anti-monotone downward pruning.
  • FP-Growth: Constructs a compact FP-tree and mines conditional pattern bases recursively. Traditional FP-tree implementations store only a head pointer in the frequency header table, requiring an O(L) traversal of the node-link chain to append each new node. In skarm, we augment each header table entry with a direct tail pointer (Figure 2). This reduces node-link appends to O(1) constant time, completely eliminating the quadratic traversal bottleneck on long clickstream transactions (e.g., BMS-POS).
  • Eclat: Performs vertical tidset intersections within prefix equivalence classes ([P]_k).
Figure 1. Algorithmic mechanics of the three mining engines packaged in skarm. (A) Apriori: iterative level-wise candidate generation (C_k = L_k-1 ⋈ L_k-1), downward-closure pruning (∀ s ⊂ c, s ∈ L_k-1), and sparse transaction support counting. (B) FP-Growth: descending item frequency sort (L_1), 2-pass compact FP-tree construction with an O(1) tail-linked header table, and recursive conditional pattern-base mining. (C) Eclat: vertical inverted transaction-ID layout (i T(i)), prefix equivalence class decomposition ([P]_k), and depth-first tidset intersections (T(X ∪ Y) = T(X) ∩ T(Y)). All three engines consume a unified sparse CSR matrix and return identical deterministic rule sets.
Figure 2. FP-tree architecture with frequency header table and the O(1) tail-pointer optimization. Standard FP-tree implementations store only a head pointer, requiring an O(L) linked-list traversal to append new nodes during tree insertion. skarm augments each header entry with a direct tail pointer, reducing node-link appends to O(1) constant time. This optimization eliminated the sequential traversal bottleneck on deep clickstream benchmarks (such as BMS-POS), enabling all 30 evaluation trials to complete smoothly with zero correctness deviations.

Scikit-Learn Estimator and Pipeline Interoperability

The primary user interface is AssociationRulesEstimator, structured around the multi-tier system architecture shown in Figure 3. It implements the full scikit-learn estimator protocol:

  • Parameters and Cloning: Constructor parameters (min_support, min_threshold, metric, algorithm, max_candidates) are stored without modification. get_params() and set_params() allow runtime inspection and dynamic parameter updates. Estimators are fully cloneable via sklearn.base.clone() and support Python pickle serialization.
  • Fitted Attributes: In accordance with scikit-learn conventions, all state learned during fit(X) is stored with a trailing underscore: frequent_itemsets_, rules_, is_degraded_, pruning_policy_, and n_features_in_.
  • Pipeline Interoperability:
    • Case A (Final Estimator): When placed as the terminal stage of a scikit-learn Pipeline, skarm consumes preprocessed sparse transactional representations from upstream transformers (e.g., TransactionEncoder).
    • Case B (Intermediate Feature Transformer): When placed as an intermediate stage, calling transform(X) projects transaction data into a binary feature matrix indicating which discovered association rules fire for each transaction, exposing get_feature_names_out() for downstream classifiers.
  • Unsupervised Model Evaluation: For hyperparameter tuning via GridSearchCV, skarm exposes an unsupervised scoring metric evaluating rule coverage and average confidence on held-out validation partitions, avoiding the need for artificial supervised labels.

Pruning Governor and Multi-Dimensional Budgets

To guard against combinatorial candidate explosions, the pruning governor monitors three orthogonal resource dimensions:

  1. Candidate Generation Budget (max_candidates, default 100,000, configured to 2,000,000 in the benchmark campaign): Halts candidate generation immediately upon reaching the cap, transitioning the run safely into DEGRADED mode.
  2. Memory Telemetry and Thresholds: Continuous 10 ms background sampling via psutil tracks peak resident set size (RSS) deltas.
  3. Execution Time Watchdog: An asynchronous 600 s timeout terminates runaway processes safely.

5. Experimental setup

The protocol was fixed before results were read. Figure 5 outlines the empirical benchmark and verification pipeline across all 25 datasets. Thresholds are matched across engines within each dataset (Table 4); a threshold is never chosen per engine. Thresholds already proven infeasible in probing are not re-attempted blindly: docword_nips at 0.30 timed out for all four engines, connect at 0.90 timed out for Apriori and killed the FP-Growth process, and BMS-POS at 0.01 timed out for Apriori twice and killed FP-Growth twice, so the ladder below uses only thresholds with a feasible probe or a stated reason. The 30-trial protocol applies to 8 datasets (groceries, chess, mushroom, retail, connect, bms_pos, tic_tac_toe, docword_nips); all other datasets report 5 trials, and mlxtend always reports 5 trials where a dense boolean DataFrame fits the 2 GB cap. Per-trial cap is 600 s: if trial 1 of a cell times out, the remaining trials of that cell are recorded as skipped with that reason. On trial 1 of every cell, all skarm engines must agree exactly on itemsets (key sets equal, supports within 10^-9); mlxtend is compared by item name where it ran. Runtime is time.perf_counter around fit on the pre-encoded matrix; encoding time is reported separately. Memory is peak RSS sampled every 10 ms minus the pre-trial baseline. Rule parameters are metric confidence, minimum threshold 0.25; estimator parameters are max_candidates = 2,000,000, sparse output, degrade on explosion. Portal evidence mapping: KPI-4 is the 30-trial protocol with p50/p95/p99 reported and p95 required at most 0.8× the baseline; KPI-2 is the rubric (at least 80/100, frozen before objective O2, two independent raters); AC-3 is the held-out partition reserved before tuning; KPI-1, KPI-3, KPI-5, and KPI-6 follow the portal contract as recorded in the acceptance report. The machine, library versions, and results commit are recorded in Appendix A from the campaign metadata. Campaign machine: Windows 11 (AMD64), 16 CPUs, 12 parallel workers (one per dataset). Python 3.12.10, scikit-learn 1.9.1, mlxtend 0.25.0, NumPy 2.5.4, pandas 3.1.0, SciPy 1.18.1. Per-trial cap 600 s; rules at confidence ≥ 0.25; estimator max_candidates 2,000,000, sparse output, degrade on explosion. Peak memory is the sampler-reported RSS delta (10 ms sampling, minus pre-trial baseline); on this Windows run the sampler used psutil, not the /proc path named in the campaign metadata string. 6. Results and discussion

Analytical verification and negative-test audit

Before any benchmark timing is trusted, the implementation was verified against an independent oracle and a negative-test suite. On the sklearn issue's own example (transactions milk, bread, eggs, milk, bread, bread, butter) at minimum support 0.5, mlxtend gives bread support 1.0, milk 0.667, and milk, bread 0.667, with rule milk ⇒ bread at confidence 1.0 and lift 1.0; skarm agrees exactly. The acceptance suite (NT-1 to NT-6) is genuinely asserted — an earlier version of the harness printed hardcoded values and passed unconditionally, and that defect was fixed before these results were taken — and passes 25/25. Brute-force cross-checks (4 random matrices × 2 thresholds × weighted/unweighted × 3 miners) show 0 mismatches. The bug-fix history (including the Eclat maximum-length off-by-one, loader defects on the accidents header, SPMF tokens, and tab-separated input, and the unstable rule sort) is recorded in the repository history (commits ff03b451, dd22782f, 904b19b3).

Runtime and Engine Scaling. Figure 6 and Table 5 illustrate the execution time profiles across all 25 benchmarks. Eclat emerges as the fastest engine on 20 of the 25 datasets, demonstrating decisive speedups (typically 5× to 10× faster than Apriori and FP-Growth) across sparse transaction collections such as retail, online_retail, bms_webview_1/2, and kosarak. On these sparse workloads, depth-first tidset intersections execute extremely fast using vectorized operations over compact transaction-ID lists.

Conversely, FP-Growth proves fastest on 5 datasets: accidents, adult_census, connect, docword_enron, and pumsb_star. These datasets exhibit high transaction densities or long transaction lengths (L̄ > 30), where vertical tidset intersections become memory-intensive while recursive conditional tree projections compress transaction prefixes effectively. Apriori, constrained by level-wise candidate generation (C_k = L_k-1 ⋈ L_k-1) and repeated full-database scans, is consistently slower across all benchmarks and exceeds the 600 s timeout on dense workloads (accidents@0.50, kosarak@0.005, and 4/5 trials of t10i4d100k@0.01).

Memory Consumption and Data Representations. Empirical Answers to Research Questions

The empirical results across all 25 benchmark datasets and 1,650 trial records directly resolve the five research questions formulated in Section 1.4:

RQ1: Algorithmic Equivalence. Table 6 provides conclusive evidence of cross-engine itemset identity. Across 42 evaluation cells and 157 evaluated engine pairs on trial 0, every single engine pair produced identical frequent itemsets with maximum support deviation Δsupp = 0.0. Where independent mlxtend runs succeeded, their outputs matched skarm byte-for-byte. This certifies that skarm's unified estimator abstraction preserves exact mathematical fidelity across three fundamentally distinct mining paradigms.

RQ2: Comparative Scaling and Performance Dynamics. Figure 6 and Table 5 demonstrate that algorithmic efficiency is governed by transactional density and average length (L̄):

  • Eclat is the fastest engine on 20 of the 25 datasets, achieving 5× to 10× speedups on sparse clickstream and retail datasets (retail, kosarak, bms_pos, online_retail). Here, depth-first vertical tidset intersections execute extremely fast over compact transaction-ID lists.
  • FP-Growth is fastest on 5 datasets (accidents, adult_census, connect, docword_enron, pumsb_star). These datasets feature high density or long transactions (L̄ > 30), where recursive conditional tree projections compress prefixes efficiently while vertical tidsets become bloated.
  • Apriori was fastest on 0 datasets, constrained by combinatorial candidate self-joins (C_k = L_k-1 ⋈ L_k-1) and repeated full-database scans, exceeding the 600 s watchdog on dense configurations (accidents@0.50, kosarak@0.005).

RQ3: Bounded-Search Safety and Recall Trade-Offs. Figure 12 and Section 6.4 demonstrate the efficacy of the candidate governor. On dense workloads where exact level-wise candidate generation exhibits severe combinatorial expansion, capping max_candidates accelerates execution by up to 15.56× (Chess, 0.2581 s vs.\ 4.016 s exact baseline) while recovering partial pattern subsets (0.60% to 17.95% itemset recall). On tree-based (FP-Growth) and vertical (Eclat) engines, candidate caps enforce explicit budget boundaries without unmonitored crashes. Most importantly, skarm transitions audibly into DEGRADED mode and records truncation events (with observed candidate counts before halting and unexplored candidates marked as unknown), eliminating silent omissions.

RQ4: Scikit-Learn Estimator and Pipeline Interoperability. As documented in Section 3.4 and Section 7, skarm adheres to scikit-learn's estimator protocol: constructor parameters are immutable until explicitly modified via set_params(), estimators are cloneable via sklearn.base.clone(), and fit state is encapsulated with trailing underscores. In Pipeline workflows, skarm operates seamlessly both as a terminal estimator and as an intermediate transformer projecting transactional data into binary rule-firing indicator features.

RQ5: Reproducibility, Auditing, and Telemetry. The campaign's 98.0% completion rate (1,617 OK trials out of 1,650, Figure 11) demonstrates high robustness. All 6 timeouts and 8 skips are audited with explicit rationale in Table 7. Fine-grained 10 ms RSS telemetry captures memory dynamics without system crashes, providing a reproducible empirical foundation across all 25 benchmark datasets.

Pruning-policy ablation: bounded versus exact

To quantify the trade-off between execution speed and completeness under candidate degradation, we conducted a bounded-versus-exact ablation study across three benchmark datasets representing distinct density regimes: dense Chess (Apriori), medium-density Adult Census (FP-Growth), and sparse BMS-POS (Eclat).

On the dense Chess benchmark (N=3,196, support threshold 0.85, exact baseline yielding 2,669 frequent itemsets and 95,482 rules in 4.016 seconds), Figure 12 illustrates the speedup-recall dynamics. Constraining max_candidates to 50 and 100 halts candidate generation at level 2 (16 frequent 1-itemsets recovered, 0.60% recall, 0 rules), accelerating execution by 13.68× (0.2935 s) and 15.56× (0.2581 s) respectively, with is_degraded_ = True. At cap 250, mining halts at level 3 (121 itemsets, 4.53% recall, 210 rules) with a 13.04× speedup (0.3080 s). At cap 500, mining reaches level 4 (479 itemsets, 17.95% recall, 2,358 rules) with a 6.59× speedup (0.6092 s). Once max_candidates reaches 1,000, the governor operates in exact mode (is_degraded_ = False), recovering all 2,669 itemsets and 95,482 rules in 4.3712 s (0.92×).

On Adult Census (N=32,561, σ=0.40, exact baseline 103 itemsets and 738 rules in 1.7273 s via FP-Growth), capping candidates at 50 recovers 51 itemsets (49.5% recall, 22 rules) in 1.7565 s (0.98× speedup), while cap 100 recovers 101 itemsets (98.1% recall, 610 rules, 82.7% rule recall) in 1.6780 s (1.03×). On sparse BMS-POS (N=515,596, σ=0.05, exact baseline 59 itemsets and 56 rules in 6.5228 s via Eclat), candidate cap 50 recovers 51 itemsets (86.4% recall, 39 rules) in 6.4658 s (1.01×), and cap 100 recovers all 59 itemsets in 6.6338 s (0.98×). These empirical measurements highlight a critical architectural trade-off: candidate bounding yields dramatic 13.68×–15.56× speedups on dense workloads subject to level-wise combinatorial explosion in Apriori, whereas on tree-compressed (FP-Growth) or vertical bitset (Eclat) engines on sparse-to-medium datasets, candidate bounding acts primarily as a safety fence against memory blowout rather than a runtime accelerator (≈ 1.0× speedup), since initial tree construction and TID-list indexing constitute the bulk of the computational cost. Crucially, across all degraded runs, skarm explicitly records degradation status, candidate counts observed before halt (with unexplored candidate counts marked as unknown), and termination causes in metadata_, ensuring bounded subsets are never conflated with exact mining.

Figure 12. Pruning policy ablation on Chess (N=3,196, minsup =0.85, 2,669 exact frequent itemsets). Bounded mode halts combinatorial candidate explosion early, delivering up to 15.56× speedups at low caps while audibly signalling degradation via is_degraded_.

7. Limitations

  • Excluded scope (portal contract). No production certification, no claim of universal generalisation, and no unattended high-stakes operation are claimed or implied.
  • Single machine, Python only. Timings come from one machine (Appendix A); they do not transfer to other hardware, and a Python implementation is not directly comparable to C/Java SPMF miners on raw speed.
  • Baselines not yet run. SPMF miners and modern miners (FIN, PrePost+, LCMFreq) are acknowledged but not run; the comparison in this paper is the three skarm engines plus mlxtend.
  • Estimator API verification. Compliance with scikit-learn's estimator protocol was verified directly: AssociationRulesEstimator implements get_params(), set_params(), is cloneable via sklearn.base.clone(), supports Python pickle serialization, and operates inside scikit-learn Pipeline and GridSearchCV workflows across scikit-learn versions 1.3 through 1.9. Running sklearn.utils.estimator_checks.check_estimator raises an assertion mandating a supervised predict() method. As established in scikit-learn issues #32712 and #2662, pattern mining is unsupervised pattern discovery rather than supervised classification; skarm adheres to scikit-learn's object and parameter lifecycle conventions without imposing synthetic supervised prediction semantics.
  • Pruning-policy trade-offs and determinism. The ablation in Section 6.4 characterizes bounded mode across three density regimes; while bounded generation provides an auditable safety governor against combinatorial explosion, execution determinism under degradation is guaranteed within the tested runtime environment via canonical enumeration order, whereas heuristic value-ranked pruning remains an area for future exploration.
  • Dataset provenance limits. Mirror licences are recorded as unknown where unstated, never guessed; two stored files differ from commonly cited counts (Section 4) and the measured figures are the ones reported.
  • Support-range limits. Results hold at the thresholds in Table 4; lower thresholds on dense sets were excluded after failed probes, so no claim is made there.

8. Conclusions

skarm packages Apriori, FP-Growth, and Eclat behind one auditable, sklearn-style estimator, with deterministic outputs, candidate telemetry, and a bounded mode that reports its own truncation. Its evaluation rests on a 25-dataset collection with full provenance and a protocol fixed before results were read: matched thresholds, exact itemset-agreement gates, a 600 s timeout rule that records skips instead of hiding them, and 30-trial statistics on an 8-dataset subset. On 25 datasets, skarm's three engines agree exactly on itemsets, apriori fastest on none; fpgrowth fastest on 5 of 25; eclat fastest on 20 of 25 at primary thresholds, with 6 timeout trials and mlxtend absent on 6 cells for stated reasons; the remaining work is the SPMF and modern-miner baselines, and the pruning-policy ablation.
