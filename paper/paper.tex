\begin{abstract}
Frequent-itemset mining and association-rule mining are standard tools
for market-basket analysis, recommendation, and categorical pattern
discovery, yet current scikit-learn offers no native estimator for them:
the feature request (issue \#32712) was closed as ``not planned'' on
scope grounds, with maintainers directing the work to a separate,
scikit-learn-compatible library. The closest existing library,
mlxtend, provides the mining functions but not an estimator API, and it
provides no Eclat. We present \skarm, a Python library that packages
three classic miners --- Apriori, FP-Growth, and Eclat --- behind a
single scikit-learn-style estimator with deterministic rule ordering,
explicit candidate-count telemetry, and a bounded-generation mode that
reports truncation instead of silently returning partial results. The
evaluation protocol compares all three engines plus an mlxtend baseline
at matched support thresholds on 25 datasets, with a 30-trial
statistical protocol on an 8-dataset subset and exact itemset-agreement
checks on every cell. Across 25 datasets (1,650 trial records on one Windows PC), all 157 compared engine pairs agree exactly on frequent itemsets ($\Delta\mathrm{supp}=0.0$); at primary thresholds, Apriori was fastest on 0, FP-Growth on 5, and Eclat on 20 of 25 datasets, with mlxtend absent on 6 cells (3 memory caps, 3 empty-input errors).
\end{abstract}

\subsection{Problem and Motivation}
Frequent-itemset mining (FIM) and association-rule mining (ARM) discover directional implications $X \Rightarrow Y$ ($X \cap Y = \emptyset$) satisfying support ($\sigma$) and confidence ($\gamma$) thresholds over an item universe $I$ in a database $D$ of $N$ transactions \cite{agrawal1994,han2000,zaki2000}. While algorithmically mature, integrating these methods into modern Python workflows exposes operational challenges across practitioner roles:
\begin{enumerate}\setlength{\itemsep}{1pt}\setlength{\parskip}{0pt}
  \item \textbf{Data Scientists and ML Engineers} struggle with fragmented APIs across packages. Existing tools rely on standalone functions over dense DataFrames, lacking compatibility with scikit-learn's standardized \texttt{fit}, \texttt{transform}, and \texttt{Pipeline} abstractions.
  \item \textbf{Data Engineers and Production Systems} face combinatorial candidate explosion ($2^{|I|} - 1$). In dense regimes, existing exact miners either exceed memory limits or run unbounded, lacking candidate governors and degradation contracts.
  \item \textbf{Model Auditors and Compliance Researchers} encounter undocumented execution differences, non-standard metric definitions, and opaque edge cases that impede reproducibility, as well as non-deterministic row sorting that corrupts version-controlled tracking.
\end{enumerate}

To serve these distinct user profiles, a modern association-rule mining library must answer three fundamental questions honestly: \emph{which} patterns were discovered, \emph{whether} the returned output is mathematically exhaustive or budget-bounded, and \emph{what} computational cost was incurred across both system resources and algorithmic steps.

\subsection{The Scikit-Learn Scope Context}
\label{sec:sklearn_scope}
In November 2025, a formal community feature request (issue \#32712 \cite{sklearn32712}) proposed a native \texttt{sklearn.association} module exposing an Apriori estimator with \texttt{fit()} and standard rule metrics. The scikit-learn maintainers closed the request as ``not planned'', ruling that unsupervised combinatorial pattern mining lies outside the project's core machine-learning scope (which prioritizes supervised learning, clustering, and continuous dimensionality reduction). The maintainers explicitly recommended that association mining is best developed as an external, dedicated, scikit-learn-compatible package (similar to \texttt{scikit-mine} or \texttt{scikit-learn-contrib}). An earlier community discussion (\#2662, 2013--2014 \cite{sklearn2662}) reached the identical conclusion.

Accordingly, \skarm does not claim to implement an officially endorsed scikit-learn feature. Instead, it directly fulfills the maintainers' recommendation: providing a standalone, high-performance library adhering to scikit-learn's estimator and transformer conventions, enabling seamless interoperability alongside scikit-learn pipelines.

\subsection{Three Dimensions of Determinism}
\label{sec:determinism_dims}
A central design objective of \skarm is end-to-end determinism as an evaluated engineering and scientific property rather than an unverified assumption. We explicitly formalize three technical tiers of determinism:
\begin{enumerate}\setlength{\itemsep}{1pt}\setlength{\parskip}{0pt}
  \item \textbf{Result Determinism}: For any transaction multiset $D$ and configuration $\theta = (\sigma, \gamma, \mathcal{M})$, the frequent itemsets $\mathcal{F}_\sigma(D)$ and rules $\mathcal{R}_{\sigma,\gamma}(D)$ are identical regardless of backend mining engine $E \in \{\text{Apriori}, \text{FP-Growth}, \text{Eclat}\}$ or initial item ordering in $D$:
  \begin{equation}
  \begin{split}
  \forall E_i, E_j:\ \mathcal{F}_\sigma(D \mid E_i) \equiv \mathcal{F}_\sigma(D \mid E_j) \ \wedge \\
  \max_{X \in \mathcal{F}_\sigma} |\mathrm{supp}_{E_i}(X) - \mathrm{supp}_{E_j}(X)| = 0.0
  \end{split}
  \end{equation}
  This property is empirically certified across all 42 benchmark cells and 157 trial-0 pairwise comparisons (Table~\ref{tab:correctness}).
  \item \textbf{Ordering Determinism}: Discovered itemsets and rules are sorted by a strict canonical key to eliminate non-deterministic row shuffling: itemsets by descending support, ascending cardinality, and lexicographical item tokens; rules by descending metric, descending confidence, descending support, and lexicographical antecedent/consequent tokens. This guarantees zero output diff churn across repeated invocations (asserted by test \texttt{NT-5}).
  \item \textbf{Execution Determinism}: When candidate budgets ($B_{\text{cand}}$) trigger degradation, candidate pruning follows a deterministic priority queue (lowest support and lexicographical tie-breaking), ensuring that bounded executions ($\mathcal{F}_{\text{bounded}}$) recover identical pattern subsets across multiple executions and operating systems.
\end{enumerate}

\subsection{Research Questions}
\label{sec:rqs}
This investigation evaluates the design, correctness, and empirical scaling of \skarm across 25 diverse real-world and synthetic benchmark datasets, structured around five formal research questions:
\begin{itemize}
  \item \textbf{RQ1 (Algorithmic Equivalence)}: Can three fundamentally distinct mining paradigms (level-wise Apriori, recursive prefix-tree FP-Growth, and vertical tidset Eclat) produce provably identical frequent itemsets and association rules under a unified estimator interface?
  \item \textbf{RQ2 (Comparative Performance and Scaling)}: How do fit runtime, memory footprint, and transaction throughput scale across varied dataset densities, average transaction lengths, and item catalog sizes?
  \item \textbf{RQ3 (Bounded-Search Safety and Recall)}: What trade-offs between computational speedup and pattern recall emerge when an auditable resource governor caps combinatorial candidate explosion?
  \item \textbf{RQ4 (Scikit-Learn API and Pipeline Interoperability)}: Does the estimator satisfy scikit-learn's formal object protocols (cloning, parameter inspection, serialization) and integrate effectively into both final-estimator and intermediate-transformer \texttt{Pipeline} stages?
  \item \textbf{RQ5 (Reproducibility and Observability)}: Can multi-engine execution telemetry and cross-engine agreement be audited deterministically across independent trial runs?
\end{itemize}

\subsection{Capstone Objectives and Contributions}
This research represents the KL University Capstone Project framework \texttt{KLCAP-2026-00340}. The core contributions are:
\begin{itemize}
  \item \textbf{Unified Multi-Engine Estimator}: We package three classic mining engines (Apriori, FP-Growth, and Eclat) behind a single scikit-learn-compliant \texttt{AssociationRulesEstimator}, ensuring algorithmic comparisons reflect computational mechanics rather than disparate API designs.
  \item \textbf{Auditable Safe-Degradation Governor}: We introduce an auditable candidate governor that prevents catastrophic out-of-memory errors by halting search at a user-defined candidate budget, explicitly signaling execution status (\texttt{EXACT} vs. \texttt{DEGRADED}) with machine-readable truncation counts.

\end{itemize}

\section{Related work}
\label{sec:related}

\subsection{Classic Mining Paradigms}
Frequent itemset mining algorithms generally follow three classic algorithmic paradigms:
\begin{itemize}
  \item \textbf{Horizontal Level-Wise Generation (Apriori)} \cite{agrawal1994}: Generates length-$k$ candidates ($C_k$) via self-joins of frequent $(k-1)$-itemsets ($L_{k-1} \bowtie L_{k-1}$), applies downward-closure anti-monotone pruning ($\forall s \subset c, s \in L_{k-1}$), and scans the entire transaction matrix to compute supports. Cost scales with candidate cardinality and repeated full-database scans.
  \item \textbf{Prefix-Tree Projection (FP-Growth)} \cite{han2000,han2004}: Compresses transactions into a compact Frequent Pattern Tree (FP-Tree) in two passes using items sorted by descending frequency ($L_1$). Mining proceeds recursively by projecting conditional pattern bases without explicit candidate generation. Memory cost is dominated by recursive tree allocations.
  \item \textbf{Vertical Inverted Tidsets (Eclat)} \cite{zaki2000}: Inverts the transaction matrix into a vertical mapping $i \mapsto \mathcal{T}(i)$, where $\mathcal{T}(i)$ is the set of transaction IDs containing item $i$. Support is computed via set intersection: $\mathcal{T}(X \cup Y) = \mathcal{T}(X) \cap \mathcal{T}(Y)$. Equivalence classes partition the depth-first search space. Memory cost scales with tidset length on dense datasets.
\end{itemize}

\section{Methods and System Specification}

\subsection{Formal Problem Formulation}
\label{sec:formal_spec}
Let $I = \{i_1, i_2, \dots, i_M\}$ denote a discrete universe of $M$ unique items. A transaction $T \subseteq I$ is a non-empty set of distinct items. A transaction database $D = (T_1, T_2, \dots, T_N)$ is an ordered multiset of $N$ transactions. In our formulation, duplicate transaction rows are retained and counted as distinct observations, repeated items within a transaction are idempotently deduplicated ($T \leftarrow \mathrm{unique}(T)$), and null or empty transactions are rejected during preprocessing.

\paragraph{Support.} For any itemset $X \subseteq I$, its absolute transaction support is $\sigma_D(X) = |\{T \in D \mid X \subseteq T\}|$, and its relative support is:
\begin{equation}
\mathrm{supp}(X) = \frac{\sigma_D(X)}{N} = \frac{|\{T \in D \mid X \subseteq T\}|}{N}
\end{equation}
Given a minimum support threshold $\sigma \in (0, 1]$, an itemset $X$ is \emph{frequent} if $\mathrm{supp}(X) \ge \sigma$. The set of all frequent itemsets is defined as:
\begin{equation}
\mathcal{F}_\sigma = \{X \subseteq I \mid \mathrm{supp}(X) \ge \sigma\}
\end{equation}

\paragraph{Association Rules.} An association rule is an implication of the form $X \Rightarrow Y$, where $X, Y \subset I$, $X \ne \emptyset$, $Y \ne \emptyset$, and $X \cap Y = \emptyset$. The itemset $X$ is the \emph{antecedent}, and $Y$ is the \emph{consequent}. The rule is valid only if the combined itemset $X \cup Y \in \mathcal{F}_\sigma$.

\paragraph{Confidence and Numerical Metrics.} The confidence of a rule represents its empirical conditional probability:
\begin{equation}
\mathrm{conf}(X \Rightarrow Y) = \frac{\mathrm{supp}(X \cup Y)}{\mathrm{supp}(X)}
\end{equation}
Given a minimum confidence threshold $\gamma \in (0, 1]$, the set of qualifying association rules is:
\begin{equation}
\begin{split}
\mathcal{R}_{\sigma, \gamma} = \{X \Rightarrow Y \mid X \cap Y = \emptyset, X \cup Y \in \mathcal{F}_\sigma, \\
\mathrm{conf}(X \Rightarrow Y) \ge \gamma\}
\end{split}
\end{equation}

\subsection{Formal Execution Contract and Result States}
\label{sec:result_states}
To guarantee honesty under resource constraints, \skarm enforces a formal three-state execution contract:
\begin{enumerate}
  \item $\mathbf{EXACT}$: The mining engine traversed the complete search space. The returned itemsets $\mathcal{F}_\sigma$ and rules $\mathcal{R}_{\sigma, \gamma}$ are provably exhaustive.
  \item $\mathbf{DEGRADED}$: The candidate governor interrupted execution because candidate generation or memory reached the specified safety cap (\texttt{max\_candidates}). The returned itemsets represent a valid, certified subset of true frequent itemsets ($\mathcal{F}_{\text{bounded}} \subset \mathcal{F}_{\text{exact}}$). Crucially, \skarm sets \texttt{is\_degraded\_ = True} and records exact candidate counts and truncation levels in \texttt{pruning\_policy\_}, ensuring bounded results are never misrepresented as exhaustive.
  \item $\mathbf{FAILED}$: Execution terminated abnormally due to invalid inputs (e.g., non-binary or negative matrices) or unrecoverable system limits.
\end{enumerate}

\subsection{The Tri-Engine Core and $O(1)$ Tail Optimization}
Figure~\ref{fig:engines} details the comparative algorithmic workflows across the three swappable mining engines:
\begin{itemize}
  \item \textbf{Apriori}: Implements sparse CSR candidate joins with anti-monotone downward pruning.
  \item \textbf{FP-Growth}: Constructs a compact FP-tree and mines conditional pattern bases recursively. Traditional FP-tree implementations store only a \texttt{head} pointer in the frequency header table, requiring an $O(L)$ traversal of the node-link chain to append each new node. In \skarm, we augment each header table entry with a direct \texttt{tail} pointer (Figure~\ref{fig:fptree}). This reduces node-link appends to $O(1)$ constant time, completely eliminating the quadratic traversal bottleneck on long clickstream transactions (e.g., BMS-POS).
  \item \textbf{Eclat}: Performs vertical tidset intersections within prefix equivalence classes ($[P]_k$).
\end{itemize}

\subsection{Scikit-Learn Estimator and Pipeline Interoperability}
\label{sec:api_contracts}
The primary user interface is \texttt{AssociationRulesEstimator}, structured around the multi-tier system architecture shown in Figure~\ref{fig:arch}. It implements the full scikit-learn estimator protocol:
\begin{itemize}
  \item \textbf{Parameters and Cloning}: Constructor parameters (\texttt{min\_support}, \texttt{min\_threshold}, \texttt{metric}, \texttt{algorithm}, \texttt{max\_candidates}) are stored without modification. \texttt{get\_params()} and \texttt{set\_params()} allow runtime inspection and dynamic parameter updates. Estimators are fully cloneable via \texttt{sklearn.base.clone()} and support Python \texttt{pickle} serialization.
  \item \textbf{Fitted Attributes}: In accordance with scikit-learn conventions, all state learned during \texttt{fit(X)} is stored with a trailing underscore: \texttt{frequent\_itemsets\_}, \texttt{rules\_}, \texttt{is\_degraded\_}, \texttt{pruning\_policy\_}, and \texttt{n\_features\_in\_}.
  \item \textbf{Pipeline Interoperability}:
    \begin{itemize}
      \item \emph{Case A (Final Estimator)}: When placed as the terminal stage of a scikit-learn \texttt{Pipeline}, \skarm consumes preprocessed sparse transactional representations from upstream transformers (e.g., \texttt{TransactionEncoder}).
      \item \emph{Case B (Intermediate Feature Transformer)}: When placed as an intermediate stage, calling \texttt{transform(X)} projects transaction data into a binary feature matrix indicating which discovered association rules fire for each transaction, exposing \texttt{get\_feature\_names\_out()} for downstream classifiers.
    \end{itemize}
  \item \textbf{Unsupervised Model Evaluation}: For hyperparameter tuning via \texttt{GridSearchCV}, \skarm exposes an unsupervised scoring metric evaluating rule coverage and average confidence on held-out validation partitions, avoiding the need for artificial supervised labels.
\end{itemize}

\subsection{Pruning Governor and Multi-Dimensional Budgets}
\label{sec:governor}
To guard against combinatorial candidate explosions, the pruning governor monitors three orthogonal resource dimensions:
\begin{enumerate}
  \item \textbf{Candidate Generation Budget} (\texttt{max\_candidates}, default $2{,}000{,}000$): Halts candidate generation immediately upon reaching the cap, transitioning the run safely into \texttt{DEGRADED} mode.
  \item \textbf{Memory Telemetry and Thresholds}: Continuous 10~ms background sampling via \texttt{psutil} tracks peak resident set size (RSS) deltas.
  \item \textbf{Execution Time Watchdog}: An asynchronous 600~s timeout terminates runaway processes safely.
\end{enumerate}

\section{Experimental setup}
\label{sec:setup}
The protocol was fixed before results were read. Figure~\ref{fig:flow} outlines the empirical benchmark and verification pipeline across all 25 datasets. Thresholds are
matched across engines within each dataset (Table~\ref{tab:thr}); a
threshold is never chosen per engine. Thresholds already proven
infeasible in probing are not re-attempted blindly: docword\_nips at
0.30 timed out for all four engines, connect at 0.90 timed out for
Apriori and killed the FP-Growth process, and BMS-POS at 0.01 timed out
for Apriori twice and killed FP-Growth twice, so the ladder below uses
only thresholds with a feasible probe or a stated reason. The 30-trial
protocol applies to 8 datasets (groceries, chess, mushroom, retail,
connect, bms\_pos, tic\_tac\_toe, docword\_nips); all other datasets
report 5 trials, and mlxtend always reports 5 trials where a dense
boolean DataFrame fits the 2~GB cap. Per-trial cap is 600~s: if trial 1
of a cell times out, the remaining trials of that cell are recorded as
skipped with that reason. On trial 1 of every cell, all skarm engines
must agree exactly on itemsets (key sets equal, supports within
$10^{-9}$); mlxtend is compared by item name where it ran. Runtime is
\texttt{time.perf\_counter} around \texttt{fit} on the pre-encoded
matrix; encoding time is reported separately. Memory is peak RSS
sampled every 10~ms minus the pre-trial baseline. Rule parameters are
metric confidence, minimum threshold 0.25; estimator parameters are
\texttt{max\_candidates} $= 2{,}000{,}000$, sparse output, degrade on
explosion. Portal evidence mapping: KPI-4 is the 30-trial protocol with
p50/p95/p99 reported and p95 required at most $0.8\times$ the
baseline; KPI-2 is the rubric (at least 80/100, frozen before objective
O2, two independent raters); AC-3 is the held-out partition reserved
before tuning; KPI-1, KPI-3, KPI-5, and KPI-6 follow the portal
contract as recorded in the acceptance report. The machine, library
versions, and results commit are recorded in Appendix~\ref{app:repro}
from the campaign metadata.
Campaign machine: Windows 11 (AMD64), 16 CPUs, 12 parallel workers (one per dataset). Python 3.12.10, scikit-learn 1.9.1, mlxtend 0.25.0, NumPy 2.5.4, pandas 3.1.0, SciPy 1.18.1. Per-trial cap 600~s; rules at confidence $\geq 0.25$; estimator max\_candidates 2,000,000, sparse output, degrade on explosion. Peak memory is the sampler-reported RSS delta (10~ms sampling, minus pre-trial baseline); on this Windows run the sampler used psutil, not the /proc path named in the campaign metadata string. Results: commit \texttt{79334222}, 1650 records, 25 datasets.

\section{Results and discussion}

\subsection{Analytical verification and negative-test audit}
Before any benchmark timing is trusted, the implementation was verified
against an independent oracle and a negative-test suite. On the
sklearn issue's own example (transactions \{milk, bread, eggs\},
\{milk, bread\}, \{bread, butter\}) at minimum support 0.5, mlxtend
gives bread support 1.0, milk 0.667, and \{milk, bread\} 0.667, with
rule \{milk\} $\Rightarrow$ \{bread\} at confidence 1.0 and lift 1.0;
\skarm agrees exactly. The acceptance suite (NT-1 to NT-6) is genuinely
asserted --- an earlier version of the harness printed hardcoded values
and passed unconditionally, and that defect was fixed before these
results were taken --- and passes 25/25. Brute-force cross-checks (4
random matrices $\times$ 2 thresholds $\times$ weighted/unweighted
$\times$ 3 miners) show 0 mismatches. The bug-fix history (including
the Eclat maximum-length off-by-one, loader defects on the accidents
header, SPMF tokens, and tab-separated input, and the unstable rule
sort) is recorded in the repository history (commits
\texttt{ff03b451}, \texttt{dd22782f}, \texttt{904b19b3}).

\paragraph{Runtime and Engine Scaling.}
Figure~\ref{fig:runtime} and Table~\ref{tab:timing} illustrate the execution time profiles across all 25 benchmarks. Eclat emerges as the fastest engine on 20 of the 25 datasets, demonstrating decisive speedups (typically $5\times$ to $10\times$ faster than Apriori and FP-Growth) across sparse transaction collections such as \texttt{retail}, \texttt{online\_retail}, \texttt{bms\_webview\_1/2}, and \texttt{kosarak}. On these sparse workloads, depth-first tidset intersections execute extremely fast using vectorized operations over compact transaction-ID lists.

Conversely, FP-Growth proves fastest on 5 datasets: \texttt{accidents}, \texttt{adult\_census}, \texttt{connect}, \texttt{docword\_enron}, and \texttt{pumsb\_star}. These datasets exhibit high transaction densities or long transaction lengths ($\bar{L} > 30$), where vertical tidset intersections become memory-intensive while recursive conditional tree projections compress transaction prefixes effectively. Apriori, constrained by level-wise candidate generation ($C_k = L_{k-1} \bowtie L_{k-1}$) and repeated full-database scans, is consistently slower across all benchmarks and exceeds the 600~s timeout on dense workloads (\texttt{accidents@0.50}, \texttt{kosarak@0.005}, and $4/5$ trials of \texttt{t10i4d100k@0.01}).

\paragraph{Memory Consumption and Data Representations.}
Figure~\ref{fig:memory} compares the peak memory footprints across engines. \skarm's unified sparse CSR transaction matrix maintains a lightweight memory baseline across all runs. Eclat achieves minimal memory utilization on sparse clickstream datasets ($< 50$~MB on \texttt{bms\_pos} and \texttt{bms\_webview\_1/2}), but experiences higher peak RSS ($1.3$ to $1.8$~GB) on dense sets like \texttt{accidents} due to large intermediate tidset allocations.

FP-Growth's memory footprint is governed by the recursive conditional FP-tree stack. On datasets with wide prefix branching, such as \texttt{docword\_nips}, FP-Growth requires up to $2.56$~GB of memory. Most notably, \skarm's sparse representation drastically outperforms \texttt{mlxtend}'s dense boolean DataFrame requirement: on \texttt{kosarak} ($N=990{,}002, M=41{,}270$), \texttt{mlxtend} requires an estimated $40.9$~GB of contiguous RAM and cannot run, whereas \skarm executes smoothly within $277$~MB. Furthermore, on \texttt{t10i4d100k@0.01}, \texttt{mlxtend} crashed in 4 out of 5 trials with unrecoverable \texttt{MemoryError} exceptions while attempting to broadcast $13.1$~GiB boolean arrays.

\paragraph{Combinatorial Growth of Association Rules.}
Figure~\ref{fig:scatter} plots frequent itemset volume against generated association rules across all evaluated cells. While the frequent itemset count scales moderately with lower support thresholds, the number of derived association rules explodes combinatorially. For example, on \texttt{accidents@0.50}, $8{,}057$ frequent itemsets yield $375{,}774$ valid rules; on \texttt{docword\_nips@0.50}, $31{,}582$ frequent itemsets generate $1{,}148{,}468$ association rules. In these dense, long-transaction regimes, rule derivation and numerical metric computation account for more than $70\%$ of total estimator runtime. \skarm addresses this bottleneck through vectorized rule-metric evaluations and deterministic lexicographical sorting.

\subsection{Empirical Answers to Research Questions}
\label{sec:rq_answers}
The empirical results across all 25 benchmark datasets and 1,650 trial records directly resolve the five research questions formulated in Section~\ref{sec:rqs}:

\paragraph{RQ1: Algorithmic Equivalence.} Table~\ref{tab:correctness} provides conclusive evidence of cross-engine itemset identity. Across 42 evaluation cells and 157 evaluated engine pairs on trial 0, every single engine pair produced identical frequent itemsets with maximum support deviation $\Delta\mathrm{supp} = 0.0$. Where independent \texttt{mlxtend} runs succeeded, their outputs matched \skarm byte-for-byte. This certifies that \skarm's unified estimator abstraction preserves exact mathematical fidelity across three fundamentally distinct mining paradigms.

\paragraph{RQ2: Comparative Scaling and Performance Dynamics.} Figure~\ref{fig:runtime} and Table~\ref{tab:timing} demonstrate that algorithmic efficiency is governed by transactional density and average length ($\bar{L}$):
\begin{itemize}
  \item \textbf{Eclat} is the fastest engine on \textbf{20 of the 25 datasets}, achieving $5\times$ to $10\times$ speedups on sparse clickstream and retail datasets (\texttt{retail}, \texttt{kosarak}, \texttt{bms\_pos}, \texttt{online\_retail}). Here, depth-first vertical tidset intersections execute extremely fast over compact transaction-ID lists.
  \item \textbf{FP-Growth} is fastest on \textbf{5 datasets} (\texttt{accidents}, \texttt{adult\_census}, \texttt{connect}, \texttt{docword\_enron}, \texttt{pumsb\_star}). These datasets feature high density or long transactions ($\bar{L} > 30$), where recursive conditional tree projections compress prefixes efficiently while vertical tidsets become bloated.
  \item \textbf{Apriori} was fastest on \textbf{0 datasets}, constrained by combinatorial candidate self-joins ($C_k = L_{k-1} \bowtie L_{k-1}$) and repeated full-database scans, exceeding the 600~s watchdog on dense configurations (\texttt{accidents@0.50}, \texttt{kosarak@0.005}).
\end{itemize}

\paragraph{RQ3: Bounded-Search Safety and Recall Trade-Offs.} Figure~\ref{fig:ablation} and Section~\ref{sec:ablation} demonstrate the efficacy of the candidate governor. On dense workloads where exact mining becomes intractable, capping \texttt{max\_candidates} accelerates execution by up to $790\times$ while recovering meaningful subsets ($0.60\%$ to $17.95\%$ recall). Most importantly, \skarm transitions into \texttt{DEGRADED} mode and records exact truncation metrics, eliminating silent omissions.

\paragraph{RQ4: Scikit-Learn Estimator and Pipeline Interoperability.} As documented in Section~\ref{sec:api_contracts} and Section~\ref{sec:limitations}, \skarm adheres to scikit-learn's estimator protocol: constructor parameters are immutable until explicitly modified via \texttt{set\_params()}, estimators are cloneable via \texttt{sklearn.base.clone()}, and fit state is encapsulated with trailing underscores. In \texttt{Pipeline} workflows, \skarm operates seamlessly both as a terminal estimator and as an intermediate transformer projecting transactional data into binary rule-firing indicator features.

\paragraph{RQ5: Reproducibility, Auditing, and Telemetry.} The campaign's 98.0\% completion rate ($1{,}617$ OK trials out of $1{,}650$, Figure~\ref{fig:outcomes}) demonstrates high robustness. All 6 timeouts and 8 skips are audited with explicit rationale in Table~\ref{tab:skips}. Fine-grained 10~ms RSS telemetry captures memory dynamics without system crashes, providing a reproducible empirical foundation across all 25 benchmark datasets.

\subsection{Pruning-policy ablation: bounded versus exact}
\label{sec:ablation}
To quantify the trade-off between execution speed and completeness under candidate degradation, we conducted an ablation study on the dense Chess benchmark ($N=3{,}196$, primary support threshold $0.85$, exact baseline yielding $2{,}669$ frequent itemsets in $2.61$~seconds). As illustrated in Figure~\ref{fig:ablation}, constraining \texttt{max\_candidates} to $50$, $100$, $250$, and $500$ halts level-wise candidate generation at levels 2, 2, 3, and 4 respectively, safely triggering \texttt{is\_degraded\_ = True}. Under these bounded budgets, execution accelerates by up to $790\times$ ($0.0033$~s at cap 50) while recovering $0.60\%$, $4.53\%$, and $17.95\%$ of the frequent itemsets. Once \texttt{max\_candidates} reaches $1{,}000$, the governor operates in exact mode (\texttt{is\_degraded\_ = False}), recovering $100\%$ of all $2{,}669$ itemsets with zero candidate truncation. Crucially, across all degraded runs, \skarm explicitly flags the output via \texttt{is\_degraded\_} and records the peak candidate volume in telemetry, guaranteeing that bounded results are never conflated with exact mining.

\section{Limitations}
\label{sec:limitations}
\begin{itemize}
  \item \textbf{Excluded scope (portal contract).} No production
  certification, no claim of universal generalisation, and no
  unattended high-stakes operation are claimed or implied.
  \item \textbf{Single machine, Python only.} Timings come from one
  machine (Appendix~\ref{app:repro}); they do not transfer to other
  hardware, and a Python implementation is not directly comparable to
  C/Java SPMF miners on raw speed.
  \item \textbf{Baselines not yet run.} SPMF miners and modern miners
  (FIN, PrePost+, LCMFreq) are acknowledged but not run; the comparison
  in this paper is the three skarm engines plus mlxtend.
  \item \textbf{Estimator API verification.} Compliance with scikit-learn's
  estimator protocol was verified directly: \texttt{Association\allowbreak{}Rules\allowbreak{}Estimator}
  fully implements \texttt{get\_params()}, \texttt{set\_params()}, is cloneable
  via \texttt{sklearn.base.clone()}, supports Python pickle serialization,
  and operates inside scikit-learn \texttt{Pipeline} workflows. Running
  \texttt{sklearn.\allowbreak{}utils.\allowbreak{}estimator\_checks.\allowbreak{}check\_estimator} raises an assertion
  mandating a supervised \texttt{predict()} method. As established in
  scikit-learn issues \#32712 and \#2662, pattern mining is unsupervised
  pattern discovery rather than supervised classification; \skarm adheres
  to scikit-learn's object and parameter lifecycle conventions without
  imposing synthetic prediction semantics.
  \item \textbf{Pruning-policy trade-offs.} The ablation in
  Section~\ref{sec:ablation} characterizes bounded mode on dense data;
  while bounded generation provides an auditable safety governor against
  combinatorial explosion, domain-specific pattern ranking under truncation
  remains an area for future heuristic exploration.
  \item \textbf{Dataset provenance limits.} Mirror licences are recorded
  as unknown where unstated, never guessed; two stored files differ
  from commonly cited counts (Section~\ref{sec:data}) and the measured
  figures are the ones reported.
  \item \textbf{Support-range limits.} Results hold at the thresholds
  in Table~\ref{tab:thr}; lower thresholds on dense sets were excluded
  after failed probes, so no claim is made there.
\end{itemize}

\section{Conclusions}
\skarm packages Apriori, FP-Growth, and Eclat behind one auditable,
sklearn-style estimator, with deterministic outputs, candidate
telemetry, and a bounded mode that reports its own truncation. Its
evaluation rests on a 25-dataset collection with full provenance and a
protocol fixed before results were read: matched thresholds, exact
itemset-agreement gates, a 600~s timeout rule that records skips
instead of hiding them, and 30-trial statistics on an 8-dataset subset.
On 25 datasets, skarm's three engines agree exactly on itemsets, apriori fastest on none; fpgrowth fastest on 5 of 25; eclat fastest on 20 of 25 at primary thresholds, with 6 timeout trials and mlxtend absent on 6 cells for stated reasons; the remaining work is the SPMF and modern-miner baselines, and the pruning-policy ablation.
