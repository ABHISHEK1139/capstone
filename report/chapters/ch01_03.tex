The engineering motivation originates directly from an open-source ecosystem demand documented in \textbf{scikit-learn GitHub Issue \#32712} (\emph{``Add Apriori Algorithm for Association Rule Mining''}) \cite{sklearn32712}:
\begin{itemize}
  \item \textbf{Upstream Custodian}: \texttt{scikit-learn/\protect\allowbreak{}scikit-learn} repository namespace.
  \item \textbf{Direct Locator}: \url{https://github.com/scikit-learn/scikit-learn/issues/32712} (opened 14~November~2025; status re-verified 24~November~2026).
  \item \textbf{Confirmed Resolution}: Closed as \texttt{not\_\protect\allowbreak{}planned} on 16~November~2025 by maintainer \texttt{@virchan}, referencing earlier architectural ruling \#2662 (2013--2014) \cite{sklearn2662}. Core maintainers confirmed that unsupervised frequent-itemset and association-rule mining sits outside core \texttt{scikit-learn}'s scope and recommended implementation inside an independent, \texttt{scikit-learn}-compatible third-party package (such as \texttt{scikit-mine} or \texttt{scikit-learn-contrib}).
\end{itemize}

Accordingly, \skarm makes no claim of upstream endorsement or inclusion within \texttt{scikit-learn} core; rather, it follows maintainer guidance verbatim by delivering a standalone, \texttt{scikit-learn}-compatible estimator package that resolves the algorithmic, memory-bounding, and API deficits observed in existing tools.

\section{Stakeholders, Operating Context and Baseline Pain Points}
The primary beneficiaries of \skarm are machine learning engineers, data scientists, analytics researchers, and technical reviewers operating Python~3.10+ data pipelines over transactional, clickstream, market-basket, or high-dimensional categorical datasets. No external commercial sponsor or funding organization is claimed.

Within the baseline Python ecosystem prior to this project, practitioners faced four interconnected operational pain points:
\begin{enumerate}
  \item \textbf{Dense Matrix Memory Blow-Up}: The predominant Python package, \texttt{mlxtend} (v0.25.0) \cite{mlxtend}, consumes dense pandas DataFrames where memory scales as $\mathcal{O}(N \times M)$. On sparse high-cardinality logs such as Kosarak ($990{,}002 \times 41{,}270$), a dense boolean frame requires $40.9$~GB, causing immediate out-of-memory failures.
  \item \textbf{Absence of Vertical Bitset Mining and Pipeline Integration}: \texttt{mlxtend} exposes procedural functions without \texttt{BaseEstimator} compliance, preventing \texttt{clone()}, \texttt{GridSearchCV}, or \texttt{Pipeline} composition, and omits Eclat vertical intersections.
  \item \textbf{Unbounded Combinatorial Candidate Explosion}: Classic Apriori candidate sets scale exponentially up to $\mathcal{O}(2^M)$ on dense corpora, crashing long-running processes without explicit resource budgets or diagnostic warnings.
  \item \textbf{Opaque Rule Semantics and Non-Determinism}: Ad-hoc implementations differ on edge cases (e.g., division-by-zero in conviction and Zhang's metric) and emit dictionary-order-dependent rows that break reproducible diffing and audits.
\end{enumerate}

\section{Approved Problem Statement, Mandate and Final Goal}
\textbf{Approved Problem Statement:} Practical association-rule mining requires controlled candidate growth, reproducible weighted and sparse support counting, clear numerical rule-quality semantics, and conformance to standard machine learning pipeline interfaces. Existing open-source tools either reject native estimator encapsulation or fail silently under dense candidate explosion, yielding predictions and rule sets that cannot be trusted under cross-industry benchmarking conditions.

\begin{klbox}[KLDarkBlue]
\textbf{One-Sentence Project Goal (Approved Mandate):} Deliver a \texttt{scikit-learn}-compatible frequent-itemset and association-rule mining Python estimator (\skarm) built upon a mathematically verified Apriori baseline, enhanced with sparse FP-Growth and vertical bitset Eclat engines, auditable pruning budgets, and deterministic six-metric verification across adversarial and large-scale workloads.
\end{klbox}

\section{Scientific and Technical Literature}
Frequent-itemset mining (FIM) formalizes pattern discovery over a binary transaction database $\mathcal{D}$ by enumerating all itemsets $X \subseteq \mathcal{I}$ satisfying $\mathrm{supp}(X) \ge \sigma$. Three classical algorithmic paradigms anchor the field:
\begin{enumerate}
  \item \textbf{Horizontal Level-Wise Candidate Generation (Apriori)}: Agrawal and Srikant \cite{agrawal1994} introduced the anti-monotonicity (downward-closure) property ensuring every subset of a frequent itemset is frequent. Apriori joins $L_{k-1} \bowtie L_{k-1}$ to construct candidates $C_k$, prunes invalid candidates, and performs $k$ database passes. While conceptually auditable, level-wise joins trigger candidate explosion on dense workloads with low support thresholds.
  \item \textbf{Prefix-Tree Pattern Growth (FP-Growth \& FP-Array)}: Han, Pei, and Yin \cite{han2000,han2004} eliminated explicit $C_k$ generation via a two-pass compressed prefix tree (FP-Tree) linked through a frequency-ordered header table. Grahne and Zhu \cite{grahne2005} further demonstrated that an FP-Array matrix of pairwise frequent counts accelerates 2-itemset enumeration and conditional projection without dynamic tree traversal overhead.
  \item \textbf{Vertical TID-Set \& Bitset Intersections (Eclat)}: Zaki \emph{et al.} \cite{zaki1997,zaki2000} inverted the incidence layout so each item maps to a vertical transaction-ID list ($\mathcal{T}(i)$), partitioning the search space into disjoint prefix equivalence classes $[P]_k$ traversed depth-first via $\mathcal{T}(X \cup Y) = \mathcal{T}(X) \cap \mathcal{T}(Y)$. Modern dense/sparse refinements replace raw integer sets with contiguous bitsets or diffsets.
  \item \textbf{Recent Comparative Algorithmic Studies (2022--2025)}: Fournier-Viger \emph{et al.} \cite{fournier2022} synthesized modern scalability challenges in pattern mining (memory exhaustion, reproducibility, and dynamic thresholds). Kallay and Mihoc \cite{kallay2025} compared Apriori, Eclat, FP-Growth, FIN, PrePost+, and LCMFreq, confirming that specialized node-set and closure algorithms (FIN, PrePost+, LCMFreq) reduce runtime overhead in compiled Java/C implementations while remaining algorithmically equivalent on exact frequent itemsets.
  \item \textbf{Association Rule Interestingness Semantics}: Hahsler \cite{hahsler} standardized mathematical definitions and boundary behaviors for support, confidence, lift, leverage, conviction, and Zhang's association metric ($\in [-1, +1]$), highlighting how zero-denominator edge cases create silent divergences when unspecified.
\end{enumerate}

\section{Limitations, Contradictions and Unresolved Needs}
Empirical literature exhibits conflicting claims over whether FP-Growth or Eclat dominates across sparse versus dense corpora, largely because prior evaluations compare implementations across heterogeneous languages, dense vs.\ sparse containers, or mismatched threshold grids. Furthermore, academic papers rarely report failed probes, timeout cells, or explicit candidate counts under truncated runs, leaving practitioners without an auditable contract when exact mining becomes intractable.

\section{Evidence-Backed Gap Statement}
No actively maintained, native Python library bridges the gap left by \texttt{scikit-learn} issue \#32712 by uniting horizontal (Apriori), pattern-growth (FP-Growth), and vertical bitset (Eclat) miners behind one sparse-native \texttt{scikit-learn} estimator with deterministic canonical sorting, machine-precision weighted metrics, and fail-safe \texttt{EXACT}/\texttt{DEGRADED} candidate-explosion governance.

\section{Positioning and Baseline Selection}
To prevent circular self-validation, \skarm retains three rigorous baselines re-used in Chapter~7:
\begin{enumerate}
  \item \textbf{Internal Reference Baseline (\texttt{O2})}: Canonical level-wise Apriori algorithm in \texttt{skarm/\protect\allowbreak{}apriori.py}, evaluated unchanged under identical CSR matrices.
  \item \textbf{Primary Python Baseline}: \texttt{mlxtend} (v0.25.0) across all 25 datasets and representative external comparisons.
  \item \textbf{Cross-Language State-of-the-Art Baseline}: Compiled Java~21 SPMF miners (\textsc{FIN}, \textsc{PrePost+}, \textsc{LCMFreq}, and \textsc{FP-Growth}) on representative dense, medium, and sparse corpora.
\end{enumerate}

\section{Consequences for Requirements, Design and Validation}
These literature findings impose three strict architectural consequences: (1)~all engines must share one CSR encoding layer so speedups measure algorithmic work rather than serialization artifacts; (2)~a unified pruning governor must intercept candidate/memory growth before OS OOM occurs and label truncated fits explicitly; and (3)~verification must audit canonical key identity ($\Delta_{\mathrm{supp}}=0.0$) rather than itemset counts alone.

All 25 benchmark corpora reside or download cleanly into \texttt{data/\protect\allowbreak{}} with exact measured file statistics ($N$, $M$, $\bar{L}$, density $\rho = \bar{L}/M \times 100\%$) verified by direct parser inspection rather than copied from external web tables (\texttt{DATASET\_\protect\allowbreak{}INVENTORY.md}, accessed 29~October~2026). \section{External Interfaces and Compatibility Obligations}
External contracts comprise: (1)~\textbf{Estimator Python API}: \texttt{Association\protect\allowbreak{}Rules\protect\allowbreak{}Estimator(min\_\protect\allowbreak{}support, metric, min\_\protect\allowbreak{}threshold, algorithm, max\_\protect\allowbreak{}len, max\_\protect\allowbreak{}candidates, max\_\protect\allowbreak{}time\_\protect\allowbreak{}seconds, max\_\protect\allowbreak{}memory\_\protect\allowbreak{}mb, on\_\protect\allowbreak{}candidate\_\protect\allowbreak{}explosion, sparse\_\protect\allowbreak{}output)} exposing \texttt{fit(X, y=None, sample\_\protect\allowbreak{}weight=None)}, \texttt{transform(X)}, \texttt{predict(X)}, \texttt{get\_\protect\allowbreak{}feature\_\protect\allowbreak{}names\_\protect\allowbreak{}out()}, \texttt{get\_\protect\allowbreak{}params()}, and \texttt{set\_\protect\allowbreak{}params()}; (2)~\textbf{CLI}: \texttt{python -m skarm.cli --dataset ... --algorithm ...}; and (3)~\textbf{Data Ingestion}: dense NumPy \texttt{ndarray}, SciPy \texttt{csr\_\protect\allowbreak{}matrix}/\texttt{csc\_\protect\allowbreak{}matrix}, pandas \texttt{DataFrame}, or Python list/generator transaction streams.

\section{Trust Boundaries, Security and Input Validation}
Although \skarm performs local in-process computation with no network socket or authentication server, untrusted input matrices establish a formal validation boundary. Non-binary continuous floats, NaN/Inf tokens, complex arrays, 1D vectors, negative sample weights, and out-of-range thresholds ($\sigma \notin [0,1]$) are explicitly rejected via \texttt{Boundary\protect\allowbreak{}Condition\protect\allowbreak{}Error} (subclass of \texttt{ValueError}) or \texttt{TypeError}. Crucially, \skarm never performs silent float binarization that could hide upstream data corruption. Memory-exhaustion denial-of-service vectors on dense inputs are mitigated via the cooperative \texttt{PruningPolicy} budget watchdog.

\section{Algorithmic Correctness and Analytical Oracle Criteria}
Every mining engine must satisfy pairwise identity ($\Delta_{\mathrm{supp}} = 0.0$ within $10^{-9}$ tolerance) across shared CSR matrices. Analytical rule-metric correctness (\texttt{KPI-2}) is scored deterministically against closed-form analytical fixtures (\texttt{ORACLE\_\protect\allowbreak{}RULES\_\protect\allowbreak{}0\_\protect\allowbreak{}4\_\protect\allowbreak{}CONF\_\protect\allowbreak{}0\_\protect\allowbreak{}6}): $\text{Score} = 100.0$ if $\Delta_{\max} < 10^{-9}$, $90.0$ if $< 10^{-6}$, $70.0$ if $< 10^{-4}$, else $0.0$ (passing threshold $\ge 80.0/100$).

\section{Deployment and Operational Environment}
Target environment: Python~3.10--3.12 on Windows~11 or Linux x86\_64 with locked scientific dependencies (\texttt{requirements.txt}) and GitHub Actions CI (\texttt{.github/\protect\allowbreak{}workflows/\protect\allowbreak{}ci.yml}). No daemon processes, elevated privileges, or external database servers are required.
